## 💡 الفكرة

منجز **لا يستبدل أبشر**. المعاملة تبدأ وتُعالَج على أبشر كالمعتاد — منجز يتدخل فقط بعد أن تتعثر المعاملة ويُكتب رمز تعثر داخلي في النظام الأساسي. بدل أن يبقى الرمز مجرد سطر في قاعدة بيانات لا أحد يتصرف بناءً عليه، يقرأه منجز فورًا وينفّذ الإجراء المناسب:

- **إن كانت المشكلة قابلة للحل آليًا** (شرط ناقص، بيانات غير متطابقة، طلب مكرر، تعثر تكامل مؤقت...) → يُنفَّذ الحل، يُتحقق منه، وتُغلق المعاملة — قبل أن تتحول إلى غرامة أو مراجعة يدوية.
- **إن كانت الحالة حساسة أو تتجاوز حد المحاولات** → تُصعَّد مباشرة لموظف بملف كامل جاهز (السبب، الأدلة، التوصية) بدل أن يبدأ الموظف التحقيق من الصفر.

كل خطوة من هذا المسار تُسجَّل في قاعدة البيانات لحظة حدوثها — فـ"رحلة الطلب" التي يراها المستفيد ليست عرضًا بصريًا، هي قراءة حقيقية من سجل تدقيق فعلي.

## ✨ الميزات الأربع الأساسية

### 1. لوحة المتابعة
نظرة تشغيلية شاملة: إجمالي الاستثناءات الحالية، ما تم حله آليًا، ما يحتاج موظف، أكثر الأسباب والأكواد تكرارًا، توقع الحمل الأسبوعي (Moving Average + Trend)، حالة الاستمرارية التشغيلية، ومحاكاة سيناريوهات الأعطال الجزئية — بالإضافة إلى ميزة "أقرب فرع أحوال لعنوانك الوطني".

### 2. معاملاتي (واجهة المستفيد)
قائمة معاملات المستفيد التي واجهت استثناءً، مع تشخيص واضح لكل معاملة: ما المشكلة، ما السبب الجذري، ما الذي فعله منجز، وما النتيجة — بالإضافة إلى "رحلة الطلب" المبنية بالكامل من سجل الأحداث الفعلي.

### 3. طلبات الموظف
طابور لا يعرض إلا الحالات التي تحتاج فعلًا قرارًا بشريًا. كل حالة مرفقة بملخص **Copilot** (محرك توليد نص مبني على قواعد حتمية يقرأ بيانات الحالة الحقيقية من قاعدة البيانات — بدون أي استدعاء لخدمة ذكاء اصطناعي خارجية، ليضمن الموثوقية الكاملة وقت العرض). أزرار اعتماد / رفض / إعادة للمراجعة تُحدّث قاعدة البيانات فعليًا وتنعكس فورًا على بقية الواجهات.

### 4. دليل التعثرات
قاموس أكواد منجز الداخلية (MUN-101 إلى MUN-600) بصيغة جدول قابل للبحث: المعنى، السبب الجذري، نوع الحل، وهل يحتاج تدخل بشري — بالإضافة إلى رسم بياني لتوزيع الحالات الفعلي.

> ⚠️ أكواد `MUN-xxx` أكواد **داخلية لمنجز فقط** — ليست أكواد أبشر أو حكومية رسمية.

## 🧠 محرك حل الاستثناءات (قلب النظام)

كل معاملة متعثرة تمر بنفس التسلسل الثابت، وكل خطوة تُكتب فورًا في جدول `transaction_history`:

```
اكتشاف الاستثناء → تشخيص السبب الجذري → تنفيذ الإجراء التصحيحي → التحقق من النتيجة → إغلاق أو تصعيد لموظف
```

الفرق الجوهري عن "إعادة المحاولة" العشوائية: كل نوع استثناء له **معالجة مختلفة فعليًا** — مثلًا عند اكتشاف "طلب مكرر" (`MUN-401`) يبحث المحرك فعليًا في قاعدة البيانات عن معاملة سابقة مكتملة لنفس المستفيد ويربط الحالة فيها، بدل مجرد إعادة إرسال الطلب.

**خط أحمر ثابت:** أي استثناء كوده `MUN-600` **لا يُنفَّذ آليًا مهما كان** — يُرفض التنفيذ الآلي على مستوى الكود نفسه في الباك إند، ويُصعَّد مباشرة لموظف بشري.

## 🛠️ التقنيات المستخدمة

| الطبقة | التقنية |
|---|---|
| Backend | Python 3 + Flask |
| قاعدة البيانات | SQLite |
| Frontend | HTML / CSS / JavaScript (Vanilla) |
| الرسوم البيانية | Chart.js |
| الاتصال | REST API بصيغة JSON |
| الاستضافة | Render |

لا توجد أي بيانات ثابتة (hardcoded) في الواجهة — كل رقم وكل نص يصل عبر `fetch()` من API حقيقي.

## 🏗️ البنية المعمارية

```
munjiz-backend/
├── frontend/
│   └── index.html          # الواجهة الكاملة (4 صفحات)
├── src/
│   ├── app.py               # نقطة تشغيل Flask
│   ├── config/
│   │   └── db.py            # الاتصال بقاعدة البيانات
│   ├── seed/
│   │   └── seed.py          # بناء الجداول + بيانات صناعية واقعية
│   ├── routes/               # طبقة الاستقبال — تستقبل الطلب وتستدعي الخدمة
│   │   ├── beneficiary_routes.py
│   │   ├── cases_routes.py
│   │   ├── codes_routes.py
│   │   ├── dashboard_routes.py
│   │   ├── forecast_routes.py
│   │   └── transactions_routes.py
│   └── services/              # طبقة المنطق — كل قرار وكل حساب هنا
│       ├── beneficiary_service.py
│       ├── cases_service.py
│       ├── codes_service.py
│       ├── dashboard_service.py
│       ├── forecast_service.py
│       ├── integration_service.py   # محاكي تكامل حكومي (Mock صريح)
│       ├── resolution_service.py    # محرك حل الاستثناءات — قلب النظام
│       └── transactions_service.py
└── requirements.txt
```

**مبدأ الفصل:** طبقة `routes` لا تحتوي أي منطق أعمال — وظيفتها فقط استقبال الطلب وإرجاع JSON. كل القرارات (هل تُحل آليًا؟ هل تُصعَّد لموظف؟) تُتخذ داخل `services`، وقواعد الحل نفسها مخزّنة كبيانات في جدول `failure_codes` (محرك قواعد Rules Engine) — لا كشرط `if` مكتوب مباشرة في الكود.

### جداول قاعدة البيانات الأساسية

| الجدول | الوصف |
|---|---|
| `users` | المستفيدون (بيانات وهمية بالكامل) |
| `transactions` | المعاملات وحالتها |
| `requirement_checks` | نتيجة فحص كل شرط لكل معاملة |
| `failure_codes` | قاموس أكواد منجز + محرك القواعد |
| `cases` | الحالة المتعثرة الفعلية المرتبطة بمعاملة |
| `transaction_history` | سجل تدقيق كامل لكل خطوة حل |
| `retry_history` | سجل محاولات إعادة المحاولة |
| `forecast_data` | بيانات تاريخية لحساب التوقع |

## 🚀 التشغيل محليًا

```bash
git clone https://github.com/Wasayfalfarraj/Munajiz.git
cd Munajiz

pip install -r requirements.txt

python src/seed/seed.py    # يبني قاعدة البيانات ويعبّئها ببيانات صناعية
python src/app.py          # يشغّل السيرفر
```

ثم افتحي `http://127.0.0.1:5000/` في المتصفح.

> ملاحظة: قاعدة البيانات تُبنى تلقائيًا عند أول تشغيل إن لم تكن موجودة — مناسب أيضًا للنشر على منصات مثل Render حيث تُمسح البيانات مع كل نشر جديد.
